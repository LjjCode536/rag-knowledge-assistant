# ADR-0004: 有据回答基线:规则生成器、低分拒答与内存查询日志

**Status**: accepted

## Context

T05 接通第一条在线问答链路:问题 → top-k 检索 → 上下文构建 → 回答 → 引用。此时还没有真实 LLM 生成(T08),又要在 M3/M6 之前先有一组可复现的"一答一拒"基线。三个契约需要先定下来:

1. **生成器如何替换**:现在用教材第 45 章的规则版 stub,后续换成真实 LLM;两者必须站在同一个窄接缝上,业务编排不感知实现。
2. **拒答边界**:向量检索总会返回 top-k(哪怕分数接近 0)。如果照单全收,无关问题会被包装成"有据回答";如果只按"有无命中"判断,又永远拒不了答。
3. **问答留痕**:T06 评估、T11 反馈闭环都需要查询日志;M3 阶段还没有 PostgreSQL,日志需要一个可替换的内存落点。

## Decision

- **生成器接缝**:服务层定义 `AnswerGenerator.generate(question, *, context)`;`context` 是编号资料文本 + 结构化来源。默认实现 `RuleBasedAnswerGenerator` 只从上下文取事实,资料为空返回统一拒答文案。T08 注入真实 LLM 实现同一协议,编排层零改动。
- **低分拒答**:配置 `qa_min_score`(默认 `0.35`)。检索命中按分数过滤,**低于阈值不进上下文、不产生引用**;无命中记 `no_hits`,有命中但全部低于阈值记 `low_score`,生成器主动拒答记 `generator_refused`。所有拒答共用唯一文案 `根据当前资料无法确认。`,外部响应不带引用。
- **查询日志**:领域模型 `QueryLog` 记录原始问题、`trace_id`、检索 hits(排名 / 分数 / 是否进入证据)、过滤条件、top-k、阈值、答案、拒答原因与端到端延迟。M3 用线程安全的内存仓储;无论回答还是拒答都落日志。生产形态由 PostgreSQL 的 `query_logs` 表接管,契约不变。
- **引用形状**:对外返回扁平引用(编号、切片、文档、文件名、标题、页码、分数);编号与生成器看到的上下文编号一一对应。txt / md 等没有页码的格式 `page_number` 为 `null`,字段始终存在。

## Consequences

- **收益**:T05 在无密钥、无真实生成器时也能跑通"一答一拒";阈值与拒答原因可测、可统计,为 T06 的拒答正确率与 T09 的生成指标提供同一口径。
- **代价**:规则版回答只覆盖教材列出的少数制度条款,其余问题退化为"最相关切片原文";规则按上下文关键词触发而不解析提问意图,真实语义生成留待 T08。
- **后续**:M4 的高级检索只替换 `RetrievalService` 内部,问答编排与查询日志字段不变;T08 换成 LLM 后,若模型以不同措辞拒答,需要扩展生成结果契约(当前规则版用统一文案精确判定);T13 将内存查询日志迁到 `query_logs` 表时,API 契约与 `QueryLogRepository` 协议保持不动。
