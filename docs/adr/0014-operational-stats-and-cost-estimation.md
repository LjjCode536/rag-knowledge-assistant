# ADR-0014: 运营统计与成本统计——查询日志为唯一统计来源,成本按配置单价估算

**Status**: accepted

## Context

M7·收口(spec,issue #17)要求:LLM 用量聚合(Token / 延迟 / 估算成本)、文档 /
切片 / 问答量 / 拒答率统计接口、`/stats` 一屏看清系统健康度。

此前系统已有三处零散的可观测面,但都答不了"系统现在健康吗、花了多少钱":

- 查询日志(`query_logs`)逐条记了 `latency_ms` / `token_usage` / `refused`,
  但只有**单条**查询接口(`GET /api/v1/query-logs`),没有聚合口径;
- `/health` 只报应用自身状态(版本 / 上游是否配置 / 缓存命中率),不报业务指标;
- 反馈闭环(T11)能算差评,差评是**质量**口径,不是**规模与成本**口径。

教材第 45 章的 `GET /enterprise-kb/stats` 给了最小形态(文档数 / 已索引
文档数 / 问答量 / 反馈数),而"生产环境还缺哪些能力"清单把**成本统计**与
**LLM 调用日志**列为待补项 —— 本迭代就是补这两项。

三个设计问题需要回答:

1. **统计从哪来**:内存里现算(重启失忆)还是从持久化数据聚合(重启不丢)?
2. **成本怎么算**:Token 用量已知,但"一个 Token 值多少钱"是配置事实还是代码事实?
3. **口径怎么定**:时间区间怎么算边界?没有样本时比率是 0 还是"未知"?

## Decision

- **统计的唯一来源是已持久化的查询日志**:`StatsRepository` 契约挂在
  `documents` / `chunks` / `query_logs` 三张生产表之上,内存实现
  (`InMemoryStatsRepository`)与 PostgreSQL 实现(`PgStatsRepository`)同契约。
  pgvector 模式下统计读真库,**重启容器不丢**;memory 与 chroma 模式的数据
  仓储仍是进程内存实现(chroma 只持久化**向量**,不持久化统计),统计随进程
  失忆,与向量库口径一致(ADR-0011)。
- **聚合下推 SQL,不在 Python 侧拉全量日志再算**:`count` / `avg` / `sum` /
  `date_trunc` 全部在数据库侧完成 —— 查询日志是唯一统计来源,量级随线上
  流量增长,全量拉取不可持续。内存实现只是同契约的基线形态。
- **区间口径统一为闭区间起点 / 开区间终点**(`created_at >= start AND
  created_at < end`),`None` 表示该侧不设界(至今全部)。开区间终点让相邻
  区间可无缝拼接、不重不漏。
- **分桶按 UTC 自然小时 / 自然日切分**(`date_trunc`):桶边界是自然边界而非
  滑动窗口,跨机器口径一致;**没有问答的桶不出现**(不补零桶)——补零桶会让
  "这段时间没人用"看起来像"用得少但有量"。
- **没有样本时比率是 `None`,不是 0**:拒答率与平均延迟在问答量为 0 时返回
  `null`。0 拒答率与"没有问答"是两件事,伪造 0 会让健康度看板在冷启动时
  显示"一切正常"。
- **成本是按配置单价的估算,不是上游账单金额**:单价(元 / 千 Token)是配置
  项(`COST_PROMPT_PRICE_PER_1K` / `COST_COMPLETION_PRICE_PER_1K`),
  prompt / completion 分段计价,合计为总成本。换模型只改配置,统计口径与
  代码无关。字段命名一律带"估算"语义(`estimated_cost` 语义,响应里
  `cost` 字段的 `currency` 明示单位)。
- **成本不混进 `/health`**:`/health` 是存活探针,统计是业务面;两者分开,
  避免业务聚合拖慢健康检查。
- **区间校验只在服务层判一次**:起点不早于终点抛 `BadRequestError`(400),
  不在 API 层重复实现 —— 两处各判一次必然漂移(带时区 / 不带时区的时间混用
  时,API 层的裸比较会抛 `TypeError` 落成 500)。
- **成本端点不收 `bucket` 参数**:成本是**区间汇总值**,分桶序列在 `/stats`
  里;同一个参数在两个端点含义不同会误导调用方。
- **答档缓存命中记零 Token**:命中时生成链路整段跳过(ADR-0013),本次请求
  零上游消耗,复制出的查询日志把 `token_usage` 归零 —— 否则统计会把首发请求
  的 Token 用量重复计入每次命中,让估算成本**高于**实际支出。
- **SQL 拼装收口在纯函数**(`build_range_clause` / `build_bucket_query` /
  `build_sum_query`):SQL 文本与**占位 / 参数顺序**可离线断言 —— 真库不可达
  的环境(无 Docker)仍能守住区间闭开边界与占位错位这两个最容易出错的点。
  真库可达时另有 `tests/test_stats_pg.py` 在 PostgreSQL 16 + pgvector 上
  验证真实聚合行为,两层互补:离线层不依赖外部服务,真库层证伪恒过的断言
  (把 jsonb 取值键改错 / 把统计仓储换回内存实现,两种变异都会被用例抓住)。

## Consequences

- **`/api/v1/stats`** 返回知识库规模(文档数 / 已索引文档数 / 切片数)+
  问答健康度(问答量 / 拒答数 / 拒答率 / 平均延迟 / Token 用量)+ 估算成本
  + 分桶时间序列,接受 `start` / `end` / `bucket` 参数(区间与粒度,`bucket`
  缺省取配置 `STATS_DEFAULT_BUCKET`);**`/api/v1/stats/cost`** 返回同一时间
  段的 Token 用量与成本明细,只接受 `start` / `end`(成本是区间汇总值)。
- **区间参数非法(起点不早于终点)返回 400 `BAD_REQUEST`**,不落 500。
  新增 `BadRequestError` 错误码类型(错误码字符串本身已存在,只补子类)。
- **拒答率口径与评估器的拒答口径不同且不混用**:本 ADR 的"拒答率"是
  **线上实际拒答占比**(查询日志里 `refused=true` 的比例),评估器的"拒答
  正确率"是黄金数据集上的判定准确率 —— 后者是质量指标,前者是运行指标,
  两者不可互相替代(T09 的口径约定)。
- **Token 用量只覆盖生成步**:查询日志记的是 `GenerationUsage`(回答生成
  消耗的 Token),不含 embedding / 检索规划 / 重排的上游消耗 —— 那几段的
  用量目前只在结构化日志里。**成本因此是"生成成本"的下界**,不是全链路
  成本;把上游各段用量一并落进查询日志是后续迭代的自然扩展点
  (查询日志表的 `token_usage` jsonb 已经能承载扩展结构)。
- **缓存命中不计入成本**:答档命中时零上游消耗,日志记零 Token(见 Decision)。
  因此成本既不重复计入缓存命中,也不会因缓存而高于实际支出 —— "生成成本
  下界"这个说法在有缓存时同样成立。
- **规则版生成器零 Token**:离线基线口径下成本恒为 0;生产口径
  (`QA_GENERATOR=llm`)才有真实金额。测试用注入的生成器替身产生确定的
  Token 用量来断言折算公式。
- **单机多实例不聚合**:统计读的是同一个库,多实例共享同一份数据,天然聚合
  —— 这是"统计来自持久化数据"相对"进程内计数"的结构性优势。
- 结构化日志不新增事件(统计是查询型读,不产生新事件类型);`/health` 响应
  `data` 形状不变。
