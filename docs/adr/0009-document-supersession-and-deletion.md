# ADR-0009: 上新即退位;删除连带清理;生命周期终态 superseded / deleted

**Status**: accepted

## Context

T10(文档版本退位与删除,对应教材第 45 章 reindex 流程)之前,重上传同标题文件会生成全新 `document_id` 的独立档案:新旧两代切片与向量**并存**于检索池,GLOSSARY 的"检索只面向最新版本"不变量不成立。同时删除文档没有任何端点,过期资料无法出库。

三个实现取舍需要记录:

1. **"同一文档"的判定**:版本无编号档案,需要身份标识把多次上传串成一条版本线。
2. **退位时点**:在上传时退位,还是等新版本 indexed 完成再切换,各有可用性代价。
3. **状态机掏空终态**:ADR-0003 说"INDEXED 暂为终态,M4+ 需要时再放开";退位与删除需要新的出边。

## Decision

- **文档身份 = (租户, 文件名)**。同租户同文件名的上传是同一知识库文档的下一版本;不同租户的同名文件是两份独立文档。`DocumentRepository` 新增 `find_latest_by_file(tenant, file_name)` 支撑该判定。
- **上新即退位**:上传请求内,新档案登记之前旧版本即完成退位——`is_latest` 置 false、状态迁移到新增终态 `superseded`、向量库与关键词通道条目被清理。检索两条通道从旧版本退位起就不再可见它,不会出现"新版本已上线、旧版本还在打分"的窗口。代价:新版本若解析 / 切片 / 向量化失败,该标识下检索面暂时为空——失败原因落 `error_message` 可查,重传即恢复;这是"检索永远不出旧内容"优先于"检索永远有内容"的取舍。
- **删除 = deleted 终态 + 级联清理**:`DELETE /api/v1/documents/{id}` 把档案迁移到新增终态 `deleted`,切片仓储、向量库、关键词通道条目与落盘文件一并清理;档案不物理删除,终态与 `deleted_at` 经 GET 可查;重复删除幂等返回。任何状态都可删除(含 failed / superseded)——删除是对该档案的兜底出口。
- **状态机增量细化(不推翻,只追加,同 ADR-0002)**:`superseded` 与 `deleted` 是跨状态的终结迁移,可以来自任意其他状态;常规管线记录中两者为终态无出边。这正式放开了 ADR-0003 中 `INDEXED` 的"暂为终态"。
- **清理失败可重试**:清理步骤先于状态翻转执行;失败时档案原状保留、原因落 `error_message`,异常包装为 `DOCUMENT_SUPERSEDE_FAILED` / `DOCUMENT_DELETE_FAILED`(500,retryable),重试即从未完成的清理步骤恢复。新错误码只追加、不改名。
- **仓储契约只加方法**:`VectorStore` / `KeywordIndex` / `ChunkRepository` 各加 `delete(document_id)`(幂等),`DocumentRepository` 加 `find_latest_by_file`;换 Chroma / pgvector / PostgreSQL 时按同一契约实现,领域层不动(ADR-0001)。

## Consequences

- 退位版本的切片记录保留:GET 切片仍能看到退位版本历史,但作为检索输入的两条通道已清空,版本残留不可能出现在任何检索结果里。
- `is_latest` 是档案层的版本可见标记,不做检索期过滤依据——旧版本数据在退位时已被物理清除,双保险式检索过滤不引入。
- 删除时档案的 `chunk_count` 摘要同步清零,报表不会读出已删除切片的余数。
- 同一实现在并发上传同一标识时:IngestionService 以进程内版本锁串行化「身份查找 → 退位 → 登记新档案」关键段(生产形态由 M3 数据库事务接管同一语义),后到的上传按现行最新串行退位,版本线不会分叉。
- 退位与删除都是终态:切片 / 向量化端点按状态校验会拒绝已退位档案再次进入管线,旧版本数据不可能在退位后重新进入检索池。
