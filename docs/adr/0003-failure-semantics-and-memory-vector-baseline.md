# ADR-0003: 向量化失败不落 failed;内存向量库为 M3 基线;过滤在检索前

**Status**: accepted

## Context

M3 首个落点(T04)把"切片 → 向量化 → 内存向量库入库 → 相似度检索"打通。三处实现存在真实取舍:

1. **失败语义**:解析(M1)、切片(M2)失败会落 `failed` 状态;但向量化调用的是模型服务上游,失败多为未配置密钥 / 限流 / 超时等**可重试**因素。若沿用了 failed 落点,一次抖动就把文档打成终态,须另设"复活"迁移才能重试。
2. **向量库后端**:M3 计划三级存储(内存 → Chroma → pgvector)。第一层需要的是"注册可被检索的最小正确语义",而非持久化。
3. **过滤时点**:切片携带租户 / 部门等权限元数据,同类基线实现常见的"检索后过滤"会先算相似度再丢弃,浪费计算,更会让被排除文档占据 top-k 名额导致召回不足。

## Decision

- **上游失败不落 failed**:向量化与检索中的上游错误统一映射为 `AppError` 家族信封返回;文档停在 `chunked`,重试即可。`EMBEDDING` 是请求内经状态机校验的瞬时态(`chunked → embedding → indexed`),M7 引入异步 ingestion 时才开始在外部可观察。
- **内存向量库是 M3 基线**:`VectorStore` 契约在领域层(`app/domain/retrieval.py`),重嵌即整组替换(与切片整组替换对齐,ADR-0002),先过滤候选后算余弦。换 Chroma / pgvector 只替换实现,契约与指标口径不动。
- **检索前过滤**:元数据过滤(租户 / 部门 / 文档类型 / 版本 / 文档)发生在相似度计算之前——被过滤候选不参与打分与排名,也不再被写入结果。

## Consequences

- `UnifiedLLMClient.embed(texts)` 本就支持批量输入:一个文档的全部切片一次请求打完,用量与延迟由统一客户端与服务层(`document_embedded`)双层结构化日志。
- 状态机为 `chunked` 追加 `→ embedding`;`INDEXED` 暂为终态(重切片只能从 `chunked` 发起,M4+ 需要时再放开)。
- 更换向量模型导致维度不一致时,内存实现按"相似度 0,不参与有效排序"处理而不是报错;真实重生产形态(Chroma / pgvector)由存储自行约束维度,调用方应重嵌整个知识库。
