# ADR-0021: 文档级授权与检索前允许集合;默认不可读

**Status**: accepted

## Context

现状的 `department` / `doc_type` 只是元数据筛选维度:任何调用方都能改筛选条件,因此它们不是权限。系统没有"谁能看哪份文档"的授权模型,也没有文档级 ACL。

好消息是接缝已经对:过滤发生在相似度计算之前,被排除的切片不参与打分、不占 top-k。要补的是身份到文档的授权关系,以及把它解析成检索前的允许集合。

## Decision

1. **默认不可读(deny-by-default)。** 一份知识库文档对某主体可见,当且仅当:同租户,且满足下列之一 —— 主体是租户 `admin`;主体是文档所有者;存在一条生效的文档授权,其授权主体是"该用户""该用户所属部门"或"该租户"。
2. **部门授权比对的是主体的部门声明,不是文档的 `department` 字段。** 文档的 `department` 仍是元数据与收窄条件;`doc_type` 永远不是权限来源。
3. **授权只做允许。** 文档授权记录"授权主体 + 逻辑文档",没有拒绝条目;撤销即删除记录。授权主体三类:用户、部门、整个租户。
4. **授权挂在逻辑文档上,不随版本退位失效。** 术语表里"版本 = 同一份知识库文档的一次内容修订",而版本退位会生成新的文档记录 id;若授权按记录 id 存,重传一次就让所有被授权者失去访问。授权因此以(租户 + 文件名)标识逻辑文档,Scope 解析时展开为现行版本的文档集合。文档删除是终态,连带删除其授权,审计事件保留。
5. **默认可见范围与授予者。** 新上传文档默认仅文档所有者与租户 `admin` 可见;"发布到租户"就是一条租户级授权。授予/撤销只能由所有者或 `admin` 发起,`member` 不能给别人的文档授权。
6. **检索前解析为允许集合。** 授权仓储把(主体, 租户)解析成允许的文档集合;检索范围增加"文档集合"这一集合型条件(IN 语义),三套向量库与关键词索引同步实现,过滤仍在打分之前。**空集合表示一条都查不到,绝不表示"不限制"**。
7. **授权变更立即失效答档缓存。** 正确性优先于缓存命中率;按文档精细失效留作量级上来后的优化。
8. **前端 v1 只做文档详情页的授权清单。** 所有者/管理员可查看、添加、移除授权;不做用户目录搜索、批量授权与审计检索。
9. **平台管理员可越过文档授权**,但只在其跨租户管理动作中,并逐次审计。

## Considered Options

- **只做部门/文档类型 ABAC**:复用现有元数据、成本最低,但做不到"这份文档只给这几个人";不满足文档权限的要求。
- **引入通用策略引擎(Casbin / OPA)**:策略可配置,但检索热路径需要先把策略反解成文档集合,策略引擎在这一步帮不上忙,只多一层 DSL;放弃。策略表达力不够时再评估。
- **按记录 id 存授权**:实现最直白,但重传即丢授权,与"版本"的定义冲突;放弃。
- **post-filter(检索后过滤)**:会破坏 top-k 语义并泄漏存在性;拒绝。

## Consequences

- **`ChunkFilter` 是破坏性变更**:从"等值单值、可选"变成"必填范围 + 集合条件",三套向量库、关键词索引、评估器与测试替身同步改。语义仍是"过滤先于打分"。
- **万级文档以上,IN 列表会变重**;备选方案是给切片打访问标签(department / doc_type / access_tags)做交集过滤。本 ADR 不实施,记为扩展点。
- **上传表单语义变化**:租户与部门不再是自由字段;部门默认取上传者的部门声明,只有 `admin` 能指定成别的部门。
- **评估口径变化**:权限边界用例改为"租户 A 的主体 + 租户 B 的同主题诱饵";评估请求携带按租户签发的真实 JWT,无过滤对照只在评估模块内部使用(用租户 B 的主体发起),不进 HTTP。权限边界通过率继续作为门禁指标。
- **授权不随历史版本消失**:检索只面向现行版本,退位版本的授权记录随逻辑文档保留,不影响结果。
- **已知边界**:主体离开组织后无法再通过认证,但其用户级授权记录不会自动清理;不做离职联动(显式出界)。
